# Nexus Repository REST API alignment review

Reference: Sonatype Nexus Repository 3.97.0-13. The canonical machine-readable surface is the
`/service/rest/swagger.json` document exposed by every Nexus instance; the endpoint inventory used
here comes from the official `sonatype-nexus-community/nexus-repo-api-client-go` client generated
from that specification.

The raw comparison table lives in [`nexus-rest-api-inventory.md`](nexus-rest-api-inventory.md).
That file is generated by matching the 459 Nexus `/service/rest/v1` method/path pairs against the
annotations of the kkRepo staging branch. A `no` entry means the Nexus-shaped path is absent;
functional equivalents may exist under `/internal`.

## Headline

- 459 Nexus `/service/rest/v1` method/path pairs; kkRepo exposes 52 exact matches.
- The core read surface is aligned: `status` (3/3), `assets` (3/3), `components` (3/4) and
  `routing-rules` (5/5).
- Most management operations are implemented in kkRepo under **custom `/internal/*` endpoints**
  (`/internal/repositories`, `/internal/security`, `/internal/blob-stores`, `/internal/cleanup`,
  `/internal/security/scanning`, `/internal/migration/nexus`). They are usable by the admin UI but
  are not compatible with Nexus automation.
- The main compatibility gaps are repository configuration (216 Nexus paths), security (62),
  blob stores (20), tasks/capabilities/cleanup-policies/tags/system (35), search (5) and
  lifecycle/legacy staging (5).

## Repositories

Nexus exposes two generic endpoints plus format-specific configuration:

- `GET /v1/repositories`, `GET /v1/repositories/{name}`, `GET /v1/repositorySettings`
- `POST|GET|PUT|DELETE /v1/repositories/{format}/{type}[/{name}]` for every supported format
- `DELETE /v1/repositories/{name}`, `DELETE /v1/repositories/{name}/browse`,
  `DELETE /v1/repositories/{name}/health-check`

kkRepo currently provides `GET /v1/repositories` and `GET /v1/repositories/{name}` and manages the
rest through `/internal/repositories`. The internal payload is kkRepo-specific, so Nexus
Infrastructure-as-Code scripts cannot create or update repositories.

Recommendation:

1. Add `PUT`/`DELETE /v1/repositories/{name}` backed by `RepositoryService`.
2. Add `GET /v1/repositorySettings`.
3. Add generic `/v1/repositories/{format}/{type}` handlers with a shared envelope, then
   format-specific request records for the formats kkRepo supports (maven2, npm, pypi, go, helm,
   cargo, pub, composer, terraform, swift, docker, nuget, rubygems, yum, apt, alpine, r, conda,
   conan, ansiblegalaxy, gitlfs, raw, arch, openvsx).
4. Implement browse/health-check delete semantics or return a documented 404.

## Security

Aligned (34): users (CRUD, change-password), user sources, roles (CRUD), privileges (list/get,
application/wildcard/repository-admin/repository-view/repository-content-selector create/update),
content selectors, realms active/available, anonymous.

Missing (62), grouped by feature:

| Feature | Missing paths | Recommendation |
| --- | ---: | --- |
| user tokens / service account tokens | 6 | add token CRUD; map to `api_key` infrastructure |
| SAML | 7 | only if SSO is in scope |
| LDAP (verify, order, cache, templates) | 15 | add verify/connection diagnostics if LDAP is supported |
| Atlassian Crowd | 3 | only if Crowd is required |
| OIDC user mapping | 3 | map to existing OIDC realm configuration |
| SSL truststore | 4 | expose existing trust configuration |
| IP allowlist | 10 | implement or document as unsupported |
| JWT / SSRF protection | 2 | evaluate |
| `roles/assignable`, `privileges/script` | 2 | add `roles/assignable`; keep script disabled |

Permissions must keep the `nexus:security:*` names used by Nexus; kkRepo currently maps most of
them, so the new endpoints should reuse the same privileges.

## Blob stores

Nexus exposes S3, file, Azure, Google, group and convert/test endpoints (20). kkRepo has S3 and
file store implementations but only custom `/internal/blob-stores` routes. Recommendation: add
`/v1/blobstores/s3` and `/v1/blobstores/file` create/get/update/delete plus
`/v1/blobstores/{name}` delete, mapping to the existing configuration model. Azure/Google can stay
unsupported (explicit 400/404) until those adapters exist.

## Operations: tasks, capabilities, cleanup policies, tags, system

- **Tasks**: expose a read-only Nexus view over the existing Quartz jobs (`GET /v1/tasks`,
  `GET /v1/tasks/{id}`, `POST /v1/tasks/{id}/run|stop`). Do not expose the Nexus task schema
  verbatim; map type/state/currentState.
- **Capabilities**: only needed if capabilities are part of the product model; otherwise return a
  documented empty list.
- **Cleanup policies**: alias `/v1/cleanup-policies` to the existing `/internal/cleanup/policies`
  service with Nexus schemas.
- **Tags**: map to the existing component tagging model if it becomes a product requirement.
- **System**: add `/v1/system/information`, `/v1/system/check` and `/v1/status` root (the latter is
  currently missing while `/status/check` and `/status/writable` are aligned).

## Search

Nexus exposes `GET /v1/search` (components), `/v1/search/assets` (aligned),
`/v1/search/assets/download`, `/v1/search/repositories`, `/v1/search/suggest` and
`/v1/search/versions`.

Recommendation: implement `/v1/search` and `/v1/search/repositories` first (the UI and automation
use them for discovery), then `/v1/search/assets/download` (redirect to the asset
`downloadUrl`). `suggest`/`versions` are optional.

## Staging and lifecycle

Nexus has a legacy staging API (`POST /v1/staging/move/{destination}`, `POST /v1/staging/delete`)
and a lifecycle API (`GET|PUT /v1/lifecycle/phase`, `PUT /v1/lifecycle/bounce`). kkRepo implements
session-based staging (`/v1/staging/sessions/...`) with richer semantics. Recommendation: keep the
session API and add compatibility shims for the legacy move/delete calls, or explicitly document
the divergence and return 404/405.

## Components and assets

Assets are fully aligned (list/get/delete). Components are aligned for list/get/upload; the missing
piece is `DELETE /v1/components/{id}`. Adding it requires defining component deletion semantics per
format (asset cascade vs explicit protection), which should reuse the existing repository cleanup
guards.

## Behavior to verify against a real instance

The path inventory cannot prove wire compatibility. Before claiming alignment for an endpoint,
compare against a Nexus instance and add a `compat-test` case for:

- `continuationToken` paging (request parameter and response field), including invalid/foreign
  tokens; kkRepo already implements this for assets/components.
- Error payload shape and status codes (`400`, `401`, `403`, `404`, `409`), including validation
  messages.
- Permission mapping: `nexus:*` privileges must gate the same operations; anonymous access rules.
- Content types and upload formats (`multipart/form-data` for `/v1/components`, JSON for
  repository configuration).
- Response headers used by clients (`Location`, `Content-Type`, `X-Siesta-Token` if still emitted
  by the target Nexus version).

## Deliberate non-goals

- `/v1/script`: executing arbitrary Groovy is a remote-code-execution surface and is not part of
  the kkRepo security model. If compatibility is mandatory, gate it behind an explicit,
  admin-only, disabled-by-default flag.
- OrientDB/Elasticsearch-specific endpoints and internal task/karaf APIs.
- Azure/Google blob stores until those storage adapters exist.

## Suggested roadmap

| Priority | Work | Why |
| --- | --- | --- |
| P0 | `GET /v1/status` root, `GET /v1/search`, `/v1/search/repositories`, `DELETE /v1/components/{id}`, `PUT`/`DELETE /v1/repositories/{name}` | small, used by UI/automation |
| P1 | `/v1/repositorySettings`, format-specific repository CRUD, `/v1/search/assets/download`, cleanup-policy aliases, tasks read view | IaC and operations compatibility |
| P2 | security tokens/SAML/LDAP/SSL/IP allowlist, blobstore CRUD, capabilities/tags/system, legacy staging/lifecycle | deeper management parity |
| P3 | format-specific request schemas for every repository format, `script` (only if required) | full schema parity |

The inventory file should be regenerated whenever the Nexus reference version changes; keep the
comparison script with the migration/compatibility tooling rather than editing the table by hand.
