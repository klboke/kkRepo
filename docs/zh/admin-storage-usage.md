# 管理后台存储用量

Blob Stores 和 Repositories 页面提供当前用量概览。运维人员可以按存储大小定位占用最多的
Blob Store，检查待回收数据，再点击该行的“仓库”，查看归属该存储的仓库并按逻辑用量排序。
选择“全部 Blob 存储”可解除筛选。顶部汇总跟随当前筛选结果，不混入其他仓库或存储。
Blob Stores 可点击名称、Blob 数量、存储用量和待回收表头排序，再次点击切换升降序；
数值列首次点击从大到小排列，不可用的统计在两个方向都排在末尾。

| 运维问题 | 指标 / 操作 | 口径 |
| --- | --- | --- |
| 哪个存储占用最多？ | Blob 数量、存储用量、按容量排序 | 按数据库登记的对象统计，共享 Blob 只计一次，包含非制品文件对象。 |
| 删除后为什么空间没释放？ | 待回收大小及 Blob 数量 | 已软删除、尚待物理 GC 的对象，仍包含在存储用量内。 |
| 应该继续排查哪些仓库？ | 存储行的“仓库”入口 | 按配置的 Blob Store 精确筛选，再按仓库逻辑容量排序。 |
| 仓库里存了多少文件？ | Asset Count / 制品文件数 | 统计 Hosted 上传和 Proxy 缓存，包括元数据、校验文件；Group 显示 `—`，不是包数或版本数。 |
| 哪些仓库逻辑内容最多？ | 逻辑用量 | 按 Asset 累加大小，共享内容会重复计入各 Asset，不代表物理占用。 |
| 数据够新、完整吗？ | 更新时间、加载/失败标记、大小下限 | 统计快照缓存 30 秒，部分文件大小未知时显示 `≥`。 |

Hosted 统计已存上传文件，Proxy 统计本地缓存。Group 的数量和逻辑用量统一显示 `—`，
不计入用量汇总，也不参与数值排序，但仍计入匹配仓库数量；仅筛选 Group 时，用量汇总也
显示 `—`，提示为“不适用”，区别于统计失败。部分 Group 协议会持久化缓存引用或生成的
元数据：原始统计接口保留这些记录，实际登记的 Blob 仍计入 Blob Stores 用量。
待回收量反映积压，不保证可以立即释放。Blob 用量不含未登记对象、未完成上传、临时文件及
对象存储历史版本，也不代表云账单、存储桶配额或磁盘剩余空间。仓库可能通过共享内容引用
其他存储中的 Blob，因此各仓库逻辑用量之和不用于核对物理用量。

首个统计卡片显示更新时间，标题右侧 info 图标说明快照缓存和刷新行为。指标口径收在对应
卡片标题的 info 提示中，不再单独显示说明行。长存储路径和 URL
在表格内省略显示；可点击截断文字或省略号展开完整内容，或点击复制图标直接复制完整值。
能完整显示的内容不会额外出现展开图标。
展开内容在单元格内换行，不撑宽表格。HTTP 部署也支持复制；浏览器阻止复制时提示手动
选择复制，不会误报成功。

列表先显示，统计随后加载。刷新重新获取当前可用快照，不绕过 30 秒缓存。失败或缺失显示
`—`，加载中显示 `…`，确实为空才显示 `0`；统计失败不影响编辑配置。

MySQL 和 PostgreSQL 是统计真相。每个副本通过统一缓存抽象维护可重建的短期缓存，同一
副本的并发请求合并为一次查询。每次请求仍重新判定仓库管理读取权限，不使用缓存的权限
结果筛选数据。普通 Browse、可上传仓库列表及配置列表不增加聚合查询。

首版使用两条批量聚合。Blob 复用已有覆盖索引；V54 为 Asset 新增 `(repository_id, size)`
覆盖索引，MySQL 在线创建，PostgreSQL 并发创建。新增索引需要磁盘及写入维护成本，升级
应预留 I/O 余量。缓存未命中时仍需扫描库存索引，成本随数据量增长；每个活跃副本分别刷新。

参考 [Nexus 口径验证](../../compat-test/admin-storage-usage-mapping.md) 和
[百万级双库性能报告](../en/admin-storage-usage-performance.md)。历史增长、预测、配额和自动
清理建议需要持续采样数据，作为后续能力规划；本版先提供明确、可用的当前用量及排查入口。
