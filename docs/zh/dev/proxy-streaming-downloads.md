# 未缓存代理下载的可选流式模式

所有 proxy 仓库表单都有 **Allow streaming downloads** 开关，默认关闭。说明放在信息图标中，
支持鼠标悬停、键盘聚焦和点击。配置保存在现有属性 `proxy.streamingEnabled`；编辑时不传值保留
原设置，传 `false` 明确关闭。hosted/group 不增加独立开关；group 使用实际命中的 proxy 成员配置，
仍同时遵守入口 group 与来源仓库的下载策略。

这是 [#420](https://github.com/klboke/kkRepo/issues/420) 的制品下载实现。开关允许符合条件的请求
提前返回字节，并不表示每一种协议的所有响应都能流式处理。[英文文档](../../en/dev/proxy-streaming-downloads.md)
包含相同的实现边界及协议参考。

## 下载与缓存

关闭时保留原来的完整下载、校验、保存 Blob、返回响应顺序。开启后，符合条件的首次 GET 会在读取
上游时把字节交给客户端，同时写入临时文件、计算 SHA-256。使用固定大小缓冲区，客户端读取速度
会约束上游读取速度，不把整个文件放入 Java 堆。

最后一块数据要等完整长度、EOF、已知摘要和适用的包结构/坐标校验通过后才能交给客户端。随后由
有容量限制的后台线程调用已有协议 writer，保存 Blob 并通过原有事务发布缓存元数据。客户端完成
下载不需要等待对象存储。缓存保存是尽力而为：保存失败会记录 `Progressive cache fill failed`，
下次仍是缓存未命中，但不会让已经完整下载成功的客户端失败。临时文件与容量占用在任务结束后释放。

客户端会在整体校验完成前收到前面的字节。后期校验失败时终止不足声明长度的响应，让客户端重试；
不能在已经输出的数据后拼接重试或其它 group 成员的响应。上游尚未完整接收时客户端断开，会取消
该次填充并清理临时文件；已经完整校验的填充可以继续保存。若要求任何字节交付前必须扫描整个制品，
应使用原缓冲路径：来源仓库或入口 group 启用安全扫描时，不采用流式交付。

不新增下载状态表、持久化任务、共享分片或下载协调机制。各副本只持有可丢弃的临时文件和工作任务。
发布缓存时使用现有仓库行锁、版本检查、asset 唯一约束与 writer 事务；仓库配置变化、下线、删除或
其它请求已完成缓存时，旧填充不覆盖现有结果。网络传输不放在元数据事务中。多个副本可能重复回源，
但只有完整缓存可以复用。进程崩溃后未完成填充不恢复；部署应使用临时磁盘并执行常规临时目录清理。

## 生效范围

| 协议 | 支持提前交付的首次下载 |
| --- | --- |
| Raw | 文件 GET，目录与索引探测保持缓冲 |
| APT / Yum | `.deb` / `.rpm`；已知 APT 长度与 SHA-256 在完成前校验，缓存完成后绑定包索引 |
| Maven | 普通制品，排除 POM、摘要和签名旁文件 |
| npm / OHPM | 普通制品路径上的包压缩文件 |
| PyPI / Go | PyPI 包文件（排除 `.asc`）、Go module ZIP |
| Helm / Cargo / Pub | chart、crate、Pub archive；保留适用的结构、坐标和已知摘要校验 |
| Docker/OCI | SHA-256 blob；manifest 和发现接口保持缓冲 |
| NuGet / RubyGems | `.nupkg`、`.snupkg`、`.gem` |
| Composer / Terraform / Ansible Galaxy | 普通 `.zip`、`.tgz`、`.tar.gz` 制品路径 |
| Conda | `.conda`、`.tar.bz2`，已知 repodata 长度与摘要在完成前校验 |
| Swift / Conan / Alpine / R / Hugging Face | 表单保存配置；涉及生成、签名、版本协调或投影的工作流在本版仍保持缓冲 |

元数据改写和签名、内部预取、HEAD、已有缓存的刷新、未知/零长度或编码后的上游响应，以及不支持的
路径都保留原流程。流式容量用尽时也退回原流程，开关不会绕过协议检查。

首次单段 Range 请求向上游传递 `Range`、`If-Range`，并请求 identity 编码。有效 206 直接交付，不缓存
片段；不可满足的范围返回 416，If-Range 不匹配时可以返回完整 200。开启的制品路径也支持缓存命中后的
本地 Range。非法或多段 Range 保持已有处理。上游与缓存的 validator 可能不同，跨缓存发布时 If-Range
不匹配会安全地重新下载完整文件，不会拼接不同内容。本版不保留服务端未完成下载的分片供下次续传。

## 容量与运维

- `KKREPO_PROXY_STREAMING_MAX_CONCURRENT` 默认 16，按进程计算，包含排队及正在保存缓存的任务。
- `KKREPO_PROXY_STREAMING_MAX_STAGED_BYTES` 默认 20 GiB。按 Content-Length 的两倍预留，因为已有
  writer 可能再次暂存文件。这是新增流式路径的额度，不是已有所有下载路径的全局磁盘上限。
- 缓存保存使用两个工作线程和有界队列；需要为临时文件及其它上传下载预留磁盘。
- 关闭开关影响新请求。已经开始的客户端可继续完成，但仓库版本变化后，旧填充不能再发布缓存。
  缓存的原有有效期和重新验证规则不变。

性能数据、环境、原始样本和复现方式见[性能报告](proxy-streaming-performance.md)。首个响应体字节、
客户端总耗时、客户端完成后缓存可见时间分别测量；主要收益是更早看到下载进度，不会提高上游链路带宽。
